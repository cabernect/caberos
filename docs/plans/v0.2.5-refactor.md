# v0.2.5 — Maintainability Refactor

Status: WS1-WS7 implemented on `refactor/v0.2.5-cleanup`; hotfix merged from
main in `96a7300`. WS6 extracts settings tabs and conversation renderers;
deeper conversation hook decomposition remains out of scope.
The operator subsequently approved a cleanup release including a dependency
security audit and version/release-note preparation. The original refactor
scope below is retained as its implementation baseline.
Planning baseline: `main` at `8e65435` (v0.2.4) plus hotfix `a49361a`
(`fix/parallel-approval-db-lock`).
No refactor ships until each workstream passes its verification gate.
Behaviour changes are out of scope — this is structure, naming, and
deduplication only.

## Why

The codebase grew feature-first. Three modules now concentrate most of
their subsystem's complexity in single functions, which makes tracing,
review, and safe change harder than it needs to be:

- `harness/loop.py` — `Harness.run()` is ~1,030 lines (177–1211) with
  four nested closures; it is the agent loop, context assembly, compaction
  gating, model dispatch, tool mediation, and result folding in one body.
- `pipeline.py` — `handle_inbound()` is ~350 lines (299–1047) with four
  nested closures, including the event-persistence emitter that the v0.2.4
  hotfix had to lock externally.
- `capabilities/builtin.py` — one 1,425-line `register_builtin_capabilities()`
  registering 40 capabilities.

Frontend mirrors this: `ProvidersSettings.tsx` is 5,222 lines,
`Conversation.tsx` 2,959, and `lib/api.ts` hand-rolls `fetch()` in ~12
places despite having `request()`/`fetchBlob()`/`downloadFile()` helpers.

## Non-goals

- No behaviour changes, API contract changes, or new features.
- No dependency additions or upgrades within the refactor workstreams;
  targeted security updates are part of the subsequent release preparation.
- No renaming of public API routes, capability names, tool names, or
  persisted data shapes.
- No splitting of files that are large but already well-factored
  (e.g. `artifacts/formats/docx.py` is one cohesive renderer).
- The Cloudflare/bot-detection investigation stays parked.

## Workstreams

Ordered by risk. Each lands as its own commit on the v0.2.5 branch so any
piece can be reverted independently.

### WS1 — `api.ts` fetch consolidation (frontend, low risk)

Route the ~12 raw `fetch()` call sites through `request()`/
`fetchBlob()`/`downloadFile()` or two small new helpers
(`apiUpload`, `apiDownloadBlob`) where streaming/blob semantics differ.
Delete any helper that becomes unused. Verify: `npm run build`,
`npm run test`, manual smoke of upload/download/preview paths.

### WS2 — `builtin.py` domain split (backend, low risk)

Split `register_builtin_capabilities()` into per-domain registration
modules under `capabilities/builtin/` (tools, memory/knowledge, media,
browser-adjacent, misc). `builtin.py` keeps a thin aggregator importing
each `register_*` in the same order — registration order is observable
through the capability catalog, so preserve it exactly. Verify: full
backend suite; a test asserting catalog contents/order should exist or
be added.

### WS3 — `RunEventPersister` extraction (backend, medium risk)

Extract the `_persist_event`/`_persisting_emitter` closure pair from
`handle_inbound()` into a small class (working name
`pipeline/event_persistence.py`) that owns `_msg_seq`, the per-subagent
buffers, `_tool_call_receipts`, `_narration_ids`, and the shared
`run_db_lock`. The class exposes `emit(event_type, payload)`; the
pipeline keeps forwarding to the SSE emitter first. This gives the
v0.2.4 hotfix's lock a named home instead of an anonymous closure, and
makes the persistence rules unit-testable without a full pipeline run.
Verify: existing pipeline tests + the parallel-approval regression test;
add a focused unit test for receipt caching and seq ordering.

### WS4 — `Harness.run()` phase extraction (backend, highest risk — do alone)

Break the ~1,030-line method into named phases on `Harness` (or a
`RunContext` object passed between them):

1. Context assembly (KG facts, vision flag, browser profiles, skills,
   forced skills, conversation/transcript build).
2. Compaction gate (`_mint_compaction_run`, `_apply_compaction`,
   `_budget_gate` become private methods or a `CompactionGate` helper).
3. Dispatch loop (model call, streaming, overflow retry, guardrails).
4. Tool mediation (`_mediate_one`, approval batch, gather, result
   folding, failure counting).
5. Finalization (limits check, terminal surfacing, RunResult).

Constraints: keep the public `Harness.run()` signature; keep event
ordering and seq numbering identical; the nested closures capture ~15
locals, so extract a `RunState`/`RunContext` dataclass rather than
threading parameters. Land behind the full 2,000-test backend suite plus
the live-Chromium browser tests. If a phase cannot be extracted without
changing behaviour, leave it inline and document why.

### WS5 — `handle_inbound()` phase extraction (backend, after WS3)

Once the emitter is a class, the remaining `handle_inbound()` body
splits naturally: contact/session resolution (already methods),
attachment storage, manifest capture, pre-loop commit, harness
invocation + result finalization, failure marking. Target: the method
reads as a numbered pipeline matching D19's 13 steps. Verify: pipeline
tests, channel tests, scheduler tests.

### WS6 — Frontend page splits (optional, last)

`ProvidersSettings.tsx`: extract each settings tab into
`pages/settings/` components; the page becomes a tab router + shared
state hook. `Conversation.tsx`: extract `MessageRow`, `StreamingMessage`,
`ContextInfoBar`, `CompactStatusBar`, attachment/citation components into
`components/chat/`. Pure moves — no logic edits. Verify: frontend suite,
lint, build, and a visual smoke of settings + one conversation.

### WS7 — `persist_fresh_session` helper (opportunistic)

If WS3/WS5 reveal a clean shared shape for the
`async_session_factory()` + `retry_locked_transaction` boilerplate used
in ~25 places, add `db.persist_fresh_session(factory, fn, name)` and
migrate only the call sites that match exactly. Skip sites that differ —
forced uniformity is worse than honest duplication.

## Verification gates (every workstream)

- Backend: `uv run pytest` full suite green; `ruff check` + `ruff format`.
- Frontend: `npm run test`, `npm run lint`, `npm run build`.
- No public behaviour change: capability catalog, API routes, SSE event
  names/order, DB schema, and tool schemas must be byte-identical where
  observable.
- Each workstream is a separate commit; the branch is revertible per
  slice.

## Sequencing with the hotfix

`fix/parallel-approval-db-lock` (`a49361a`) merges first as its own PR —
it is a runtime fix, not refactor, and should not wait for v0.2.5.
The refactor branch starts from `main` after that merge; WS3 then
formalizes the lock the hotfix introduced.
