# v0.2 Release Plan — Trusted Local Knowledge Agents

**Release sequence:** `v0.1.3` → `v0.1.4` → `v0.1.5` → `v0.1.6` → `v0.2.0`  
**Target cadence:** one coherent release per day  
**Headline:** trusted local knowledge agents with inspectable retrieval  
**Audience:** early adopters and friends  
**Development policy:** TDD for every new feature

---

## Product promise

By v0.2, a user can add local documents to CaberOS, ask an agent a question
from the desktop or an external channel, watch the run live, receive an answer
with local citations, and inspect exactly which sources were used.

CaberOS remains the system that owns:

- agent execution and model access;
- personal memory and local knowledge;
- credentials and MCP connections;
- tool permissions and approval policy;
- external channels;
- audit, usage, and spend history.

v0.2 does **not** expose CaberOS agents as tools inside Claude, Cursor, or
another agent host. That would invert the product hierarchy, create nested LLM
calls, weaken approval semantics, and make memory attribution ambiguous.

---

## Scope

### Included

1. **Trust and data safety**
   - atomic, integrity-checked migration;
   - automatic backups and restore points;
   - persistent authentication sessions;
   - sub-agent capability narrowing;
   - configurable external-channel approval policies;
   - behavioural security and integration tests.

2. **Knowledge Vault and local RAG**
   - Markdown, text, PDF, and attachment ingestion;
   - local chunking and FTS retrieval;
   - agent/workspace scoping;
   - automatic index lifecycle;
   - citations and source inspection in chat;
   - document management and retrieval preview UI.

3. **Early-adopter usability**
   - first-run onboarding;
   - provider and model validation;
   - health and error visibility;
   - clean-machine installation verification;
   - a small operational CLI if core milestones stay on schedule.

### Explicitly deferred

- CaberOS agents exposed as an MCP server;
- executable plugin system;
- additional messaging channels;
- additional provider integrations without a concrete user need;
- vector database or embedding infrastructure;
- rich agent-generated UI / A2UI;
- full terminal dashboard or TUI;
- Windows desktop until sandbox behaviour and an identified tester justify it;
- Linux/macOS Intel builds unless an identified early adopter needs them.

A future read-only MCP server for the Knowledge Vault may make sense after RAG
is mature. It would expose knowledge, not autonomous agents.

---

## Release discipline

### Coherent outcomes, not artificial slices

A release may contain several implementation commits. Tags represent complete
user outcomes, not individual functions.

Example:

```text
test: describe migration atomicity
feat: validate imported database
feat: swap database atomically
test: cover backup restoration
feat: create automatic restore points
```

Only the complete, verified bundle receives a tag.

### TDD contract

Every behaviour-changing feature follows this sequence:

1. Write a failing test describing externally observable behaviour.
2. Run it and confirm it fails for the expected reason.
3. Implement the smallest correct change.
4. Run focused tests until green.
5. Refactor under test coverage.
6. Run the full release verification suite.

A feature and its tests land in the same commit or pull request.

### Verification before every tag

```bash
cd backend && uv run pytest -v
cd backend && uv run ruff check src/ tests/
cd backend && uv run ruff format --check src/ tests/
cd frontend && npx tsc --noEmit
cd frontend && npm run build
```

Also perform:

- focused browser smoke testing for changed frontend behaviour;
- migration integrity checks whenever storage code changes;
- a Tauri build whenever desktop-facing code changes;
- a manual real-model smoke before `v0.2.0`.

### Stop rule

The daily cadence is a target, not permission to publish a broken artifact. If
the acceptance gate is not green, keep the version untagged and fix it.

# v0.1.3 — Trust Bundle

## Outcome

CaberOS can update, migrate, restart, delegate, and process external-channel
messages without silently losing data or escalating authority.

This release combines six related trust improvements because they share one
user-facing promise: CaberOS safely preserves local state, authority, identity,
and installed software.

---

## 1. Atomic, integrity-checked migration

### Problem

The first replace-mode implementation overwrote `agentos.db` while the desktop
gateway still had an active SQLite connection and WAL state. The result was:

```text
database disk image is malformed
```

The database had to be restored manually from the development instance.

### Tests first

- export → replace import → target passes `PRAGMA integrity_check`;
- expected row and file counts survive the round trip;
- merging the same archive twice adds nothing the second time;
- malformed ZIP is rejected without touching current data;
- archive with a malformed database is rejected;
- archive preview reports database integrity and schema compatibility;
- stale `-wal` and `-shm` files do not survive a replace;
- a failed swap keeps the original database;
- export refuses to package a corrupt source database;
- archive path traversal is rejected;
- ZIP upload and expanded-size limits prevent ZIP bombs.

### Implementation

1. Export SQLite through the SQLite backup API or an equivalent consistent
   snapshot, never by raw-copying a live database file.
2. Extract imports into a temporary directory.
3. Validate ZIP paths and size limits.
4. Open the archive DB read-only and run `PRAGMA integrity_check`.
5. Validate required tables and schema compatibility.
6. Dispose active database connections.
7. Remove stale WAL/SHM state.
8. Atomically swap the validated file with `os.replace()`.
9. Keep the original database until the new one has passed validation.
10. Show integrity and compatibility in the existing Migration preview UI.

### Done when

No malformed or partially written archive can alter the target instance, and
every successful replace leaves a database that passes `integrity_check`.

---

## 2. Automatic backups and restore points

### Tests first

- replace creates a backup before changing current data;
- backup includes DB, secret key, agent homes, and workspaces;
- restore recreates the previous state and passes integrity check;
- failed import does not delete its restore point;
- retention keeps the latest configured number of backups;
- restore requires explicit confirmation in the UI.

### Implementation

Store restore points under the active app data directory:

```text
backups/
  2026-08-21T120000Z/
    agentos.db
    secret.key
    agents/
    workspaces/
    manifest.json
```

`manifest.json` records:

- CaberOS version;
- creation time;
- database schema revision;
- SHA-256 for every file;
- database integrity result.

Add backup list, create, restore, and delete endpoints. Add a Restore Points
section to Settings → Migration. Default retention is the latest five backups.

### Done when

A destructive import can be reversed from the UI without manual filesystem or
SQLite work.

---

## 3. Persistent authentication sessions

### Problem

Authentication sessions currently live in an in-memory dictionary. Gateway
restart or desktop update logs every client out.

### Tests first

- login remains valid after engine disposal and backend re-initialization;
- raw session token is not stored;
- expired session is rejected;
- logout revokes the session;
- expired sessions are cleaned;
- cookie and bearer authentication resolve the same persisted session.

### Implementation

Add `operator_sessions`:

- `token_hash`;
- `operator_id`;
- `created_at`;
- `expires_at`;
- `last_seen_at`.

Store only a cryptographic token hash. Replace the in-memory session map in
`auth.py`. Support SQLite and PostgreSQL schema paths. Clean expired sessions
at startup and periodically.

### Done when

Backend restart and desktop update preserve valid logins while expiry and
logout still revoke access correctly.

---

## 4. Sub-agent capability isolation

### Problem

The syscall mediator leaves sub-agent capability intersection as a TODO. A
sub-agent can therefore inherit more authority than its task requires.

### Tests first

- parent grants `read_file`, sub-agent requests `terminal` → denied;
- parent grants `{read_file}`, sub-agent declares `{read_file, terminal}` →
  effective set is `{read_file}`;
- nested sub-agent capabilities can only shrink;
- denied calls produce an audit record with `sub_agent_id`;
- an omitted sub-agent capability set does not mean unrestricted access.

### Implementation

- represent effective capability scope on every sub-agent run;
- intersect requested scope with the parent effective set;
- enforce the intersection before approval evaluation;
- preserve sub-agent attribution in audit records and traces.

### Done when

No sub-agent can invoke a capability outside its parent's effective authority.

---

## 5. Explicit approval policy for external channels

### Problem

External channel sessions currently bypass approvals through a hardcoded
channel check. That means Telegram, Zalo, Discord, and future channels silently
auto-approve every approval-required tool.

### Policy vocabulary

```text
auto_approve
operator
deny
```

### Tests first

- `auto_approve` executes without waiting;
- `deny` blocks approval-required tools and audits the denial;
- `operator` creates a pending approval visible in the dashboard;
- capabilities not requiring approval remain executable;
- channel policy applies only to the configured channel;
- a missing policy defaults to `deny` for newly configured channels.

### Implementation

- store policy on channel configuration or agent-channel binding;
- replace the hardcoded branch in the syscall mediator;
- expose policy clearly in the Channels UI;
- migrate existing configured channels to `auto_approve` to preserve current
  behaviour;
- default newly configured channels to `deny`.

### Done when

External-channel authority is visible, configurable, and auditable.

---

## 6. Version synchronization and signed auto-update

### Problem

Version information currently drifts across the application:

- Settings → About hardcodes `v0.1.0` in `ProvidersSettings.tsx`;
- `frontend/src-tauri/tauri.conf.json` reports `0.1.1`;
- `frontend/src-tauri/Cargo.toml` reports `0.1.1`;
- `backend/pyproject.toml` reports `0.1.1`;
- `frontend/package.json` reports `0.0.0`.

The app therefore cannot reliably show its installed version or decide whether
a GitHub release is newer. A daily release cadence also has little value if an
installed desktop app requires a manual download every day.

### Tests first

Version behaviour:

- About renders the runtime application version instead of a hardcoded string;
- web mode obtains the backend/package version without importing Tauri APIs;
- a release verification test fails when version manifests disagree;
- the version update script changes every required manifest consistently;
- semantic version comparison handles patch and minor upgrades correctly.

Updater behaviour:

- a newer signed release is reported as available;
- equal or older versions do not prompt;
- unavailable update metadata degrades quietly and leaves the app usable;
- malformed metadata shows a non-destructive error;
- an invalid artifact signature is rejected;
- choosing "Later" does not download or install;
- choosing "Download and Restart" installs only after verification;
- app restart terminates the bundled gateway cleanly before relaunch;
- manual "Check for Updates" reports both current and latest versions.

### Implementation

#### Single release-version workflow

Add one release command, for example:

```bash
./scripts/set-version.sh 0.1.3
```

It updates and verifies:

- `backend/pyproject.toml`;
- `frontend/package.json` and lockfile metadata;
- `frontend/src-tauri/Cargo.toml`;
- `frontend/src-tauri/tauri.conf.json`.

CI runs the verification form and fails on drift. The Git tag must match the
configured version before the release workflow can publish.

The About page must not contain a version literal. In desktop mode it reads the
runtime version from Tauri. In web mode it reads version metadata exposed by
the backend health/version endpoint.

#### Tauri updater

- add the supported Tauri v2 updater plugin and frontend bindings;
- configure the updater endpoint for this repository's GitHub releases;
- generate updater artifacts and update metadata in `release.yml`;
- sign update artifacts;
- keep the signing private key only in GitHub Actions secrets — never in the
  repository or packaged application;
- embed only the public verification key in the app;
- check on startup after the UI and gateway are healthy, not before login can
  render;
- expose manual checking from Settings → About;
- show release version, notes, download progress, and explicit install action;
- allow dismissal and defer installation until the user chooses to restart;
- never silently replace the running application.

Required CI secrets should include the Tauri updater signing private key and,
if used, its password. Release automation must fail rather than publish an
unsigned or partially generated update.

### UX

Settings → About shows:

```text
CaberOS v0.1.3
You're up to date
[Check for Updates]
```

When an update is available:

```text
CaberOS v0.1.4 is available
<release notes>
[Later] [Download and Restart]
```

Download and signature errors remain recoverable; the currently installed app
continues running.

### Done when

- About always displays the installed runtime version;
- pushing a valid release tag creates both the normal installer and signed
  updater metadata/artifacts;
- an installed older desktop build can discover, verify, install, and relaunch
  into the new version;
- no private signing material is present in Git history or application files.

# v0.1.4 — RAG Foundation

## Outcome

CaberOS can safely ingest local documents, index them locally, and expose a
bounded, agent-scoped `doc_search` capability.

## Architectural constraints

- SQLite FTS5 and PostgreSQL tsvector first;
- no vector database in v0.2;
- no automatic full-document prompt injection;
- retrieval is scoped to the active agent/workspace;
- every chunk preserves source metadata for citations;
- ingestion obeys the existing workspace boundary.

---

## 1. Document and chunk model

### Tests first

- Markdown chunking preserves heading context;
- chunks stay within token budget;
- consecutive chunks preserve configured overlap;
- content hashes prevent duplicate ingestion;
- re-ingestion replaces old chunks;
- document deletion cascades to chunks and search index rows.

### Data model

`Document`:

- `id`, `agent_id`, `workspace_path`, `display_name`;
- `mime_type`, `content_hash`, `size_bytes`;
- `status`, `error`, `indexed_at`, timestamps.

`DocumentChunk`:

- `id`, `document_id`, `seq`, `text`;
- `heading_path`, `page_number`, `token_count`;
- search-vector support per backend.

### Implementation

- add a Markdown-aware overlapping chunker;
- SQLite: FTS5 document-chunk index;
- PostgreSQL: tsvector + GIN;
- incremental schema support in both backends.

---

## 2. Markdown and text ingestion

### Tests first

- ingest Markdown and retrieve an exact section;
- ingest plain text and retrieve a phrase;
- unsupported binary files fail visibly without indexing garbage;
- `../../etc/passwd` and absolute paths are rejected;
- agent A cannot ingest or retrieve agent B's document;
- changed content replaces chunks and updates the hash.

### Implementation

- add `knowledge/ingest.py`;
- support UTF-8 Markdown and text;
- route paths through `WorkspaceManager.validate_path()`;
- record parser errors on document status;
- expose list, ingest, re-index, delete, and preview APIs.

---

## 3. PDF and attachment ingestion

### Tests first

- text PDF produces searchable chunks;
- page numbers survive into source metadata;
- image-only PDF reports OCR unsupported;
- supported chat attachment can be ingested;
- malformed PDF fails safely and remains visible with `status=failed`.

### Implementation

- add a vetted PDF parser dependency;
- preserve page numbers;
- connect supported chat attachments to ingestion;
- defer OCR unless a real early-adopter document requires it.

---

## 4. `doc_search` capability

### Contract

```text
name: doc_search
kind: tool
egress: false
approval: false
arguments:
  query: string
  limit?: integer
```

The model cannot supply agent, contact, or workspace identity. Those values
come from the active run/session.

### Tests first

- relevant chunk ranks ahead of a weak match;
- results are scoped to the active agent;
- model cannot request another agent's index;
- malformed queries return a bounded result;
- result includes document, path, heading/page, and chunk ID;
- retrieval is visible in run events and traces.

### Implementation

- register `doc_search` as a built-in capability;
- query FTS5 or tsvector according to active backend;
- bound result count and returned text size;
- return structured source metadata.

---

## v0.1.4 release gate

- Markdown, text, PDF, and attachment tests green;
- path escape and cross-agent isolation tests green;
- full ingestion/search round-trip works with SQLite;
- PostgreSQL query/schema path has focused coverage;
- agent answers a scripted question by calling `doc_search`;
- Ruff, typecheck, and frontend build green.

# Risks and Stop Conditions

## Migration and backup safety

Migration touches the most valuable state in CaberOS. Any failing integrity,
path traversal, atomicity, or rollback test blocks `v0.1.3`.

## Updater signing and release ordering

Auto-update introduces a software supply-chain boundary. Losing the updater
private key or publishing unsigned metadata is not a recoverable UI bug. Keep
the private key in CI secrets, retain a protected offline backup, document key
rotation before launch, and test updating from an actual older packaged build.
A tag must not be pushed until all version manifests have been synchronized;
once users install a build with updater metadata, release URLs and signing
identity become compatibility contracts.

## RAG scope creep

Do not add embeddings, a vector database, OCR, website crawling, or arbitrary
cloud-drive sync during v0.2 unless an identified early adopter cannot use the
feature without it. FTS retrieval with citations is the vertical slice.

## Frontend testing setup

The repository currently lacks substantive frontend tests. `v0.1.5` includes
Vitest/RTL setup. If setup proves larger than expected, land the test scaffold
first and keep the release untagged until the Knowledge Vault outcome is
complete.

## Platform reach

Do not claim Windows/Linux support because CI produced an artifact. CaberOS's
shell capability requires a real platform sandbox. If no safe sandbox exists,
shell must be explicitly disabled. Cross-platform desktop support is not a
v0.2 release gate.

## Minimal CLI scope

The CLI is the first cut candidate. It must not delay migration safety,
retrieval, citations, onboarding, or clean-machine verification.

## Daily cadence

A calendar date is not a release gate. Publish when the coherent outcome is
complete and verified; otherwise continue the same version without tagging.
