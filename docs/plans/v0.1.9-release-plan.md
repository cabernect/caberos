# v0.1.9 Release Plan — Background Runs and Trustworthy Agent Feedback

**Release sequence:** `v0.1.8` → `v0.1.9` → `v0.2.0`
**Release policy:** tag only coherent, verified user outcomes
**Headline:** agents can work in the background while CaberOS keeps the operator informed
**Audience:** v0.1.8 users running longer research and automation tasks
**Current base:** latest `origin/main` after v0.1.8 hotfixes

---

## Product promise

In v0.1.9, a user can start a meaningful agent task, leave the conversation, and return later without losing control or context:

- a run continues when the dashboard, browser tab, or SSE connection is no longer active;
- the operator can see whether a run is running, waiting, completed, failed, or interrupted;
- completed and failed runs create durable notifications;
- browser and desktop users can opt into platform-level completion notifications;
- a restarted gateway does not silently pretend that an interrupted run completed;
- an agent configured for Vietnamese can produce Vietnamese user-facing output and visible progress where the selected model supports it;
- long conversations expose their context cost and compact predictable, bounded history;
- Docker and Podman startup paths build and run consistently;
- the dashboard feels deliberate around active-run navigation, especially “Jump to latest”.

CaberOS remains the system that owns agent execution, permissions, approvals, memory, credentials, channels, and observability. FastAPI/REST remains the gateway/API layer, not the product core. The CLI/TUI and a deeper CaberCore extraction remain deferred.

## Scope

### Included

1. **Durable background run lifecycle**
  - Runs already keep executing when the dashboard, browser tab, or SSE connection closes — this scope is about making the *state* durable.
  - Persist explicit run states in the DB: queued, running, awaiting approval, awaiting user input, completed, failed, stopped, and interrupted.
  - On gateway startup, reconcile orphaned `running` runs — mark them as `interrupted` instead of leaving them as `running` forever.
  - Replace process-memory-only run discovery with database-backed status and recovery metadata so status polling works after the 60s in-memory window closes.
  - Preserve the existing `reason → act → observe → repeat` invariant.
  - Keep same-turn tool-call concurrency as the only concurrency exception.
  - Define what happens when a gateway restarts during model inference, a tool call, an approval wait, or persistence.
  - Make interrupted work visible and actionable instead of silently disappearing.
  - Provide a reliable way to inspect the final result after the live event stream is gone.
2. **Operator notifications**
  - Create durable notifications for successful completion, failure, interruption, approval required, and elicitation required.
  - Deduplicate notifications by run and event type.
  - Add notification actions that open the relevant conversation, run trace, approval, or elicitation.
  - Add browser notifications for users who grant permission.
  - Add native Tauri notifications for desktop users who grant permission.
  - Keep the existing in-dashboard notification center as the source of truth.
  - Do not require the dashboard to remain focused for a completion notification to be generated.
3. **Agent language behavior**
  - Inject the language instruction at a stable system-prompt boundary.
4. **Cross-runtime and desktop polish**
  - Keep Docker and Podman Compose paths working with current `uv` and frontend builds.
  - Add a repeatable container verification path for backend image build, frontend image build, health checks, and startup.
  - Keep frontend title and favicon consistently branded as CaberOS across dev, Docker, and desktop builds.
  - Refine “Jump to latest” placement and animation so it aligns with the conversation column and composer.
  - Restore the thinking toggle and effort dropdown after switching from a channel session back to a normal chat session.
  - Preserve reduced-motion behavior and keyboard accessibility.
  - Correct documentation wherever desktop-only behavior is presented as universal.
5. **MCP OAuth automatic token refresh**
  - Persist OAuth authorization-server and protected-resource metadata so reconnects can locate the token endpoint.
  - Fix the token-expiry sentinel so an expired access token is correctly treated as invalid and triggers refresh.
  - Add regression tests for token refresh with and without persisted metadata.
  - Require manual re-authorization only when the refresh token is invalid or the authorization server rejects refresh, not on every access-token expiry.
6. **MCP stdio runtime PATH resolution**
  - Resolve bare stdio commands (`npx`, `npm`, `node`, `uv`, `uvx`) against the subprocess's actual `PATH` before spawning.
  - Fall back to common install directories: `/usr/local/bin`, `/opt/homebrew/bin`, `~/.local/bin`, and a configurable `CABEROS_MCP_RUNTIME_PATH`.
  - Prepend the resolved command's directory into the child `PATH` so shebang chains (e.g. `npx` re-exec to `node`) resolve.
  - Surface actionable missing-runtime errors instead of raw `ENOENT` / `FileNotFoundError`.
  - Do not bundle or auto-download runtimes; the operator must have Node/uv installed, CaberOS must find it.
7. **Web fetch pagination**
  - Extract HTML → markdown via `trafilatura` (main-content extraction, boilerplate removed).
  - Fall back to `readability-lxml` + `markdownify` when trafilatura returns thin.
  - Apply a hard context ceiling (e.g. 50k chars) that the model cannot override.
  - Add `offset`/`has_more` so the model can read more on demand.
  - Keep `max_chars` as an optional model override, capped at the hard ceiling.
  - Skip JS rendering — browser automation is a separate v0.2 tool set.

### Explicitly deferred

- Multi-machine distributed workers and leader election.
- A general-purpose external queue such as Redis, Kafka, or Celery.
- Guaranteed resume in the middle of a non-idempotent external side effect.
- Fully autonomous runs that bypass approvals, elicitation, cost limits, or agent policy.
- Guaranteed localization of provider-native hidden reasoning tokens.
- Personalized financial advice or a built-in market-data provider.
- Browser push notifications that require a hosted push service.
- Dashboard-wide Vietnamese localization.
- CLI/TUI and deeper CaberCore extraction.
- New external channels unless required by the background-notification outcome.

## Release invariants

### Execution

- A dashboard or SSE disconnect never cancels a run.
- A gateway restart never marks an unfinished run as completed.
- Every interrupted run has a persisted terminal or recoverable state and an explanatory reason.
- A run may execute only one reasoning step at a time.
- Tool calls from one model turn are the only calls allowed to execute concurrently.
- External side effects are never replayed automatically unless the operation is explicitly idempotent.

### Notifications

- Completion, failure, and interruption notifications are persisted before delivery is attempted.
- Notification delivery failure never changes the run result.
- A notification is actionable: it identifies the run and has a valid destination.
- Browser and native notifications are opt-in and permission-aware.
- Returning to CaberOS always reveals the durable in-app notification even when platform delivery was unavailable.

### Language

- `auto` preserves current user-language matching behavior.
- An explicit agent language takes precedence for user-facing output.
- Technical names and executable content remain stable.
- Raw provider reasoning is clearly distinguished from localized agent output.
- Test fixtures do not claim guarantees that production provider behavior cannot provide.

### Context

- Context breakdown totals equal the sum of system prompt, conversation, and tool-schema tokens.
- Tool results are bounded before they consume an unbounded fraction of the next model context.
- Compaction never removes the system prompt or the current user request.
- The operator can tell when older context was compacted or omitted.

### Packaging

- Docker and Podman builds use the same repository Dockerfiles and produce a healthy stack.
- The frontend title is `CaberOS` and the favicon is the canonical CaberOS favicon.
- Desktop, Docker, and browser deployment documentation distinguishes platform-specific behavior.

## Ordered implementation plan

### Phase 0 — Baseline and decisions

1. Confirm the v0.1.8 merge and hotfix state on `origin/main`.
2. Capture the current behavior matrix for browser, Tauri, Docker, and Podman.
3. Commit to a durable worker inside the local gateway boundary; keep a separate distributed worker process deferred.
4. Commit to keeping raw provider reasoning visible and label its language behavior honestly.
5. Define the agent language field and migration/default behavior.
6. Define run recovery states and the allowed behavior for interrupted model/tool calls.
7. Land the MCP OAuth auto-refresh fix: correct the token-expiry sentinel, persist OAuth metadata, and add regression coverage.

**Output:** approved state machine, language policy, notification policy, acceptance matrix, and MCP OAuth refresh is verified.

### Phase 1 — Run lifecycle and recovery

1. Add persisted run lifecycle fields and recovery metadata.
2. Add database-backed run lookup for detached clients and completed runs.
3. Separate live event buffering from durable run/message history.
4. Add startup reconciliation that distinguishes completed, failed, stopped, and interrupted runs.
5. Add recovery UI for interrupted runs instead of only a generic failed status.
6. Verify browser-tab close, SSE disconnect, desktop minimize, desktop quit, gateway restart, and container restart behavior.

**Output:** background runs are observable and do not depend on an active UI connection.

### Phase 2 — Notification delivery

1. Emit durable completion, failure, and interruption notifications from the run lifecycle.
2. Add notification action routing to conversations and traces.
3. Add browser permission state and browser notification delivery.
4. Add Tauri permission/configuration and native notification delivery.
5. Add delivery fallback to the existing notification center.
6. Add tests for duplicate delivery, permission denial, background tabs, and notification failure.

**Output:** users can leave CaberOS and still learn when work needs attention or finishes.

### Phase 3 — Language-aware agents

1. Add an optional language field to the versioned agent configuration.
2. Add migration and UI controls for `auto`, English, and Vietnamese.
3. Inject the selected language instruction into the system prompt.
4. Localize elicitation questions, progress summaries, and report-writing instructions.
5. Keep raw provider reasoning visible and document that its language is model-dependent.
6. Add real-provider contract tests where possible and clearly separate prompt guidance from provider guarantees.

**Output:** Vietnamese agents consistently communicate in Vietnamese where CaberOS controls the text.

### Phase 4 — Context and compaction hardening

1. Add focused tests for large web, terminal, file, and MCP results.
2. Apply per-tool result limits with explicit truncation metadata.
3. Improve compaction triggers and preserve the current task plus recent tool state.
4. Expose context breakdown and compaction history in run traces.
5. Add a user-facing “start fresh context” action that preserves the session archive.
6. Add `web_fetch` pagination: system-controlled HTML→markdown extraction, hard context ceiling, `offset`/`has_more` for on-demand reading, and `max_chars` as a bounded override.
7. Verify reports remain coherent after compaction.

**Output:** research-heavy conversations remain usable without silently exceeding model context.

### Phase 5 — Cross-runtime and interaction polish

1. Add a container smoke check for Docker and Podman-compatible Compose paths.
2. Verify the current `uv` package-install sequence in CI or a repeatable local check.
3. Add frontend branding regression coverage for title and favicon.
4. Refine “Jump to latest” positioning, visual weight, keyboard focus, and reduced-motion behavior.
5. Review first-launch, data-location, Docker, local-development, and background-run documentation.
6. Fix the chat composer so the model selector re-emits default capabilities when remounted after a channel session, restoring the thinking toggle and effort dropdown.
7. Add the MCP stdio command resolver: resolve against the child `PATH`, fall back to common runtime directories, prepend the resolved directory, and provide actionable missing-runtime errors.
8. Browser-test English and Vietnamese routes plus the dashboard background-run flow.

**Output:** the common installation and chat flows feel coherent across supported runtime modes and stdio MCP servers resolve their runtime.

### Phase 6 — Release readiness

1. Synchronize backend, frontend, desktop, website, and documentation metadata to `0.1.9`.
2. Update `CHANGELOG.md` with user-facing outcomes and migration notes.
3. Run clean-machine builds for desktop, Docker, and website paths.
4. Run full backend and frontend checks.
5. Run browser verification for:
  - detached run completion;
  - failure and interruption notifications;
  - browser notification permission states;
  - Tauri notification behavior;
  - Vietnamese agent output;
  - context breakdown and compaction;
  - Jump to latest behavior.
6. Review the complete diff and request explicit approval before tagging.

**Output:** a coherent v0.1.9 candidate ready for PR review and release tagging.

## Verification matrix

### Backend

```bash
cd backend && uv run pytest -v
cd backend && uv run ruff check src/ tests/
cd backend && uv run ruff format --check src/ tests/
```

Required focused coverage:

- run survives SSE/client disconnect;
- run state after gateway restart;
- completion/failure/interruption notification persistence;
- notification deduplication;
- language instruction and default migration behavior;
- bounded tool results;
- compaction preserves current task and required tool state;
- context breakdown totals remain correct;
- MCP OAuth automatic token refresh with expired access tokens and separate authorization-server origins;
- OAuth metadata persistence and reload after gateway restart;
- stdio MCP command resolution falls back to common runtime directories and prepends the resolved directory to child `PATH`;
- missing `npx`/`uvx` runtime surfaces an actionable error instead of a raw `ENOENT`;
- `web_fetch` paginates large pages with `offset`/`has_more` and respects the hard context ceiling.

### Frontend

```bash
cd frontend && npm run test
cd frontend && npm run lint
cd frontend && npm run build
```

Required browser checks:

- start a run, navigate away, return, and inspect its result;
- browser notification granted and denied;
- notification action opens the correct run;
- Vietnamese agent produces Vietnamese final output and visible progress where applicable;
- context tooltip accurately explains the three sections;
- Jump to latest is aligned with the conversation column and composer;
- switching from a channel session back to a normal session restores the model selector, thinking toggle, and effort dropdown;
- title is `CaberOS` and favicon loads with HTTP 200.

### Containers and website

```bash
podman-compose --env-file .env.docker.example build backend frontend
podman-compose --env-file .env.docker.example up -d
curl http://localhost:8080/health
cd website && npm run build
```

Required checks:

- Docker and Podman-compatible builds complete;
- `/health` returns `{"status":"ok"}`;
- frontend title and favicon are correct inside the container;
- English and Vietnamese docs build with complete locale coverage;
- no deployment credentials or internal hostnames are present in public documentation.

## Release acceptance gate

Tag v0.1.9 only when:

- detached runs continue independently of the UI connection;
- restart/interruption behavior is persisted and truthful;
- completion, failure, and interruption notifications are durable and actionable;
- browser and desktop notification delivery is verified with permission denied as a supported path;
- explicit Vietnamese agent language produces consistent user-facing language without promising impossible provider-native reasoning translation;
- large conversations and tool results remain within a visible, tested context budget;
- Docker and Podman paths build and pass health checks;
- the frontend is branded as CaberOS everywhere;
- the chat interaction polish is browser-verified;
- switching from a channel session to a normal chat session restores the thinking toggle and effort dropdown;
- stdio MCP servers resolve `npx`/`uvx` runtimes with fallback directories and actionable missing-runtime errors;
- full backend, frontend, container, and website verification is green;
- the PR has been reviewed and explicitly approved for merge.
