# v0.1.8 Release Plan — Stable HITL and Localized Documentation

**Release sequence:** `v0.1.7` → `v0.1.8` → `v0.2.0`
**Release policy:** tag only coherent, verified user outcomes
**Headline:** reliable approval-driven runs with localized public documentation
**Audience:** v0.1.7 early adopters and new users discovering CaberOS
**Current base:** latest `origin/main`; release work lives on `fix/v0.1.8`

---

## Product promise

In v0.1.8, CaberOS should feel reliable when an agent performs real work:

- one conversation advances through **reason → act → observe → repeat**;
- multiple tool calls emitted in one model turn may run concurrently as one action step;
- approval-required calls from that step are presented as one human-approval batch;
- all decisions are collected before the approved calls execute;
- approved calls execute concurrently, while denied calls are skipped;
- temporary SQLite contention does not silently lose configuration or strand a run;
- operators receive a clear retryable error when persistence remains unavailable;
- public website and documentation are available in English plus Vietnamese (`vi`).

CaberOS remains the system that owns agent execution, permissions, approvals, memory,
credentials, channels, and observability. FastAPI/REST remains only the gateway/API
layer. The CLI/TUI remains deferred.

---

## Scope

### Included

1. **Database-lock resilience**
   - Detect transient SQLite `locked`/`busy` failures.
   - Retry complete, replayable transactions after rollback with bounded backoff.
   - Cover agent/configuration saves, approval persistence, elicitation persistence,
     and other control-plane writes where the transaction can be safely replayed.
   - Return `503 database_busy` with `Retry-After` when the retry budget is exhausted.
   - Never blindly retry external tool side effects.
   - Keep failed runs observable and recoverable after a persistence failure.

2. **Approval-batch HITL**
   - Preserve concurrent execution for tool calls from one model turn.
   - Group approval-required calls from that turn into one approval batch.
   - Prevent any call in the batch from executing until every approval is decided.
   - If one call is denied, execute the individually approved calls and deny the rest.
   - Make the UI communicate that approval is waiting on the rest of the batch.

3. **Execution-loop invariant**
   - Lock down reason → act → observe → repeat in tests and documentation.
   - Prevent tool calls from different reasoning turns from overlapping.
   - Keep same-turn parallel tool execution as the explicit narrow exception.
   - Preserve ordered tool-result insertion into the next model context.

4. **Website and documentation internationalization**
   - Keep English as the default locale.
   - Select one initial additional language before implementation.
   - Add localized marketing pages and Starlight documentation routes.
   - Add locale navigation, canonical URLs, `hreflang`, localized metadata, and
     locale-aware search/navigation behavior.
   - Translate every documentation page into Vietnamese, prioritizing getting-started,
     capabilities, permissions, MCP, security, operations, and troubleshooting content.
   - Keep technical names, capability names, API paths, and code examples stable.

5. **Release and adoption polish**
   - Synchronize backend, frontend, desktop, and website release metadata to `0.1.8`.
   - Add the v0.1.8 changelog entry and migration/update guidance where needed.
   - Verify clean-machine website and application startup paths.
   - Include the existing MCP connection-notification reliability fix in the v0.1.8
     stability bundle, not in the earlier website-only release.

### Explicitly deferred

- Dashboard/React UI localization.
- Tauri UI localization.
- Agent-generated response translation or a user language preference for model output.
- CLI/TUI work.
- New external channels or provider integrations.
- Vector database or embedding infrastructure.
- Automatic machine translation of every document without human review.
- Changing the product hierarchy or exposing CaberOS agents inside Claude/Cursor.

## Release invariants

### Execution

- A run has one active reasoning step at a time.
- Tool calls from one model turn are the only calls allowed to execute concurrently.
- The next model turn begins only after all calls from the current turn have reached a
  terminal result: completed or denied.
- Approval batching delays execution, not reasoning-turn boundaries.

### Approval

- Approval state is persisted before an in-process approval event is resolved.
- A batch is atomic from the operator’s decision perspective but not all-or-nothing
  in execution: approved calls run, denied calls do not.
- Approval timeout is treated as a denial.
- A database failure never turns an unpersisted approval into an apparent approval.

### Persistence

- Every retryable transaction rolls back before replay.
- Retries are bounded and observable in logs with an operation name.
- External side effects are not repeated automatically unless the operation is known
  to be idempotent.
- A failed final run write must not hide the fact that the run failed; startup
  reconciliation must handle runs left in `running` state.

### Localization

- English is the source locale; Vietnamese has an explicit source page for every docs route.
- URLs identify locale explicitly; technical identifiers remain untranslated.
- Search results and navigation never mix locale content silently.
- Every English documentation route has a Vietnamese source page; missing locale pages fail the build check.

## Ordered implementation plan

### Phase 0 — Release baseline and decisions

1. Confirm `origin/main` commit and create the v0.1.8 working branch.
2. Select Vietnamese (`vi`) as the first additional website/docs locale and document the choice.
3. Inventory all version sources and release-facing strings.
4. Record the acceptance matrix for SQLite, approval batching, and localization.

**Output:** approved scope, target locale, release matrix, and clean branch baseline.

### Phase 1 — Persistence safety

1. Centralize lock classification and bounded transaction replay.
2. Apply the retry seam to agent/configuration saves.
3. Apply it to approval and elicitation row creation and operator decisions.
4. Audit notification, run-finalization, scheduler, and provider writes for safe
   replayability; add retries only where the full operation can be repeated safely.
5. Add API-level `503 database_busy` responses with `Retry-After`.
6. Make frontend control-plane saves show an explicit failure and preserve/reload the
   last server-confirmed state.
7. Add startup reconciliation and observability for runs whose final write was lost.

**Output:** lock contention becomes bounded, visible, and recoverable.

### Phase 2 — Approval-batch HITL

1. Introduce a run-turn approval batch coordinator.
2. Pass the batch context through the harness/syscall boundary.
3. Create all approval requests for the model turn before releasing execution.
4. Wait for all decisions, then release approved calls concurrently.
5. Deny only calls rejected or timed out by the operator.
6. Add batch metadata to SSE events and persisted tool-call records.
7. Update the conversation UI to show one action batch, its pending count, and each
   call’s decision without implying that an approved call is already executing.
8. Verify reconnecting SSE clients can recover the batch state.

**Output:** multiple tool calls remain parallel, but human approval is coherent.

### Phase 3 — Execution-loop hardening

1. Add a regression test for concurrent same-turn calls.
2. Add a regression test proving the next model turn waits for every current-turn
   result.
3. Add failure-path tests for mixed approved/denied batches.
4. Verify tool results remain ordered in model history even when execution is parallel.
5. Update architecture documentation with the reason/act/observe/repeat invariant.

**Output:** concurrency is explicit and bounded to one reasoning step.

### Phase 4 — Website/docs localization

1. Configure the selected locale in Astro/Starlight while preserving English default.
2. Define locale route conventions and translation ownership.
3. Add locale switcher, canonical metadata, `hreflang`, and localized sitemap behavior.
4. Add translation dictionaries for shared marketing/layout strings.
5. Translate the landing page and download page.
6. Translate the documentation index and getting-started path.
7. Translate every capabilities, permissions, MCP, approval, troubleshooting,
   architecture, operations, security, and contributing page.
8. Ensure code blocks, capability names, API paths, and command examples remain stable.
9. Generate and verify Pagefind/search behavior for each locale.
10. Add a build check that every English docs route has a Vietnamese source page.

**Output:** English plus the selected locale are independently navigable,
searchable, and deployable.

### Phase 5 — Release readiness

1. Bump synchronized manifests and release metadata to `0.1.8`.
2. Update `CHANGELOG.md` with user-facing stability and localization outcomes.
3. Update release documentation and installation/update guidance.
4. Run clean-machine application and website builds.
5. Run real-model smoke testing with:
   - one no-approval tool;
   - one approval-required tool;
   - multiple approval-required calls in one turn;
   - mixed approval/denial;
   - a simulated database lock.
6. Verify desktop packaging if desktop-facing code changed.
7. Review all release diffs, then request approval before committing, pushing, or tagging.

**Output:** a coherent v0.1.8 candidate ready for PR review and release tagging.

## Verification matrix

### Backend

```bash
cd backend && uv run pytest -v
cd backend && uv run ruff check src/ tests/
cd backend && uv run ruff format --check src/ tests/
```

Required focused coverage:

- locked transaction retries after rollback;
- retry exhaustion returns a controlled failure;
- approval row creation under contention;
- approval batch waits for all decisions;
- approved and denied calls in the same batch;
- same-turn concurrency and next-turn ordering;
- startup reconciliation of interrupted runs.

### Frontend

```bash
cd frontend && npm test -- --run
cd frontend && npm run lint
cd frontend && npm run build
```

Required browser checks:

- one approval call;
- three approval calls in one model turn;
- approve all calls and observe concurrent execution;
- deny one call and observe approved calls execute;
- reload/reconnect while a batch is pending;
- localized landing page, download page, docs navigation, and search.

### Website

```bash
cd website && npm run build
```

Required checks:

- Astro diagnostics are clean;
- every supported locale builds;
- locale links, canonical URLs, and `hreflang` are correct;
- Pagefind indexes the intended locale content;
- no secrets or generated artifacts are staged.

## Release acceptance gate

Tag v0.1.8 only when:

- full backend and frontend verification is green;
- lock contention produces no silent data loss;
- multi-tool approvals wait for the complete batch;
- same-turn concurrency remains intact and next-turn execution is ordered;
- English and the selected additional locale build and navigate correctly;
- website and application versions report `0.1.8` consistently;
- clean-machine startup and update paths are verified;
- the release diff contains no unrelated work;
- the PR has been reviewed and explicitly approved for merge.
